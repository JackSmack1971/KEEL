## 1. Authority, freeze, and interpretation

This document is the **single normative authority** for the KEEL kernel redesign and every migration change that follows it. It supersedes prior documents only as forward-looking architecture or sequencing authority. Landed code, tests, ledgers, Git refs/notes, bootstrap records, and completed plans remain authoritative evidence of current and historical behavior until migrated. the archived upgrade audit, roadmap, and prior P0/P1/P2 plans are subordinate evidence maps; they may not authorize a competing architecture.

Feature expansion above the currently landed P2 schema/planning state is **frozen**. P3-P7 and D1 may not proceed as feature work. The only permitted forward work is separately governed migration, compatibility, verification, or defect remediation needed to reach this target. Planning readiness under this document is not implementation acceptance and grants no permission.

Normative terms `MUST`, `MUST NOT`, `MAY`, and `UNTIL` are binding on later changes. Any proposed exception requires an explicit amendment to this document through a separate high-risk KEEL change; a subsystem plan, schema, adapter, generated view, CLI command, or runtime component cannot override it.

## 3. North Star and ownership boundary

### 3.1 North Star

KEEL's North Star is **trustworthy high-autonomy engineering inside Codex**: Codex should be able to plan and execute substantial engineering work with increasing autonomy, while KEEL makes repository truth, intent, permission, evidence, and landed outcomes explicit, deterministic, reviewable, and Git-bound.

### 3.2 Codex owns

Codex owns intelligence, agent execution, tool use, thread and runtime behavior, and native subagents/workspaces. KEEL MUST consume observed Codex capabilities rather than recreate an agent framework, model router, scheduler, conversation manager, tool executor, sandbox, or workspace runtime. KEEL policy may restrict use of a capability, but cannot claim to supply or confine that capability.

### 3.3 KEEL owns

KEEL owns repository understanding; canonical intent and work representation; policy; authorization records and decisions; reconciliation; evidence requirements and receipts; Git-bound attestations; and verification of the landed state. These ownership areas form the kernel. Derived UX, context, reports, hooks, and CLI projections MUST read from kernel semantics and MUST NOT become alternate sources of truth.

## 4. Canonical primitives

The future kernel has exactly these semantic primitive kinds. Each has a stable, versioned identity and provenance. Serialization details are deferred, but later schemas MUST preserve these meanings.

| Primitive | Canonical meaning |
|---|---|
| `Fact` | A provenance-bearing assertion about repository, environment, runtime, or external state, including uncertainty and freshness; never permission. |
| `Requirement` | A normative obligation derived from human intent or governing policy, with source and acceptance relevance. |
| `WorkUnit` | The smallest independently governable unit of intended work, with scope, inputs, outputs, and lifecycle identity. |
| `Edge` | A typed relationship between canonical identities. Dependency is an edge type, not a parallel graph format. |
| `EffectRequest` | A request to cause a filesystem, Git, provider, deployment, communication, or other consequential effect; declaration is not authorization. |
| `CapabilityGrant` | An authority-scoped, subject-bound, issuer-attributed, time/condition-bounded permission to attempt an effect through an observed capability. |
| `EvidenceRequirement` | A subject-bound specification of evidence needed to establish a claim at a named verification boundary. |
| `EvidenceReceipt` | An immutable-content receipt for an observed result, provider, exact subject, command/input identity, environment/runtime facts, outcome, and freshness. |
| `Decision` | A provenance-bearing resolution of alternatives, conflicts, exceptions, or policy application; it identifies authority and consequences. |
| `Attestation` | A Git-bound statement that named claims and receipts apply to an exact subject tree/commit and intent digest at a named boundary. |
| `RuntimeProfile` | A conservative observation of available Codex/runtime/tool/workspace/hook trust and limitations; configuration alone cannot make it trusted. |

A record can reference other primitives only by canonical identity. Convenience objects may exist as projections, never as new primitive kinds or authorities.

## 5. Orthogonal state model

No single status field may collapse independent questions. Every applicable primitive or projection MUST expose these orthogonal dimensions, using explicit `UNKNOWN`/`NOT_APPLICABLE` outcomes where evidence does not support a stronger state:

1. **Validity** — is the record structurally and semantically well-formed under its declared schema and invariants?
2. **Knowledge** — what is known, unknown, ambiguous, conflicting, stale, inferred, or directly observed about the claim?
3. **Support** — does the installed KEEL/Codex/runtime/provider combination support interpreting or performing the requested operation?
4. **Readiness** — are dependencies, resources, capabilities, authorization, and evidence prerequisites satisfied for the named next boundary?
5. **Lifecycle** — where is the work or attestation in its governed progression (for example proposed, planned, executing, candidate-verified, integrated, landed-verified, retired)?

Transitions in one dimension MUST NOT silently mutate another. In particular: valid is not known; known is not supported; supported is not ready; ready is not authorized; candidate-verified is not landed-verified; and lifecycle completion is not evidence that an external effect occurred.

## 6. One authoritative dependency graph

The kernel MUST maintain one authoritative dependency graph composed of canonical primitives and typed `Edge` records. Change graphs, fact graphs, requirement graphs, mission graphs, evidence graphs, resource graphs, and landing graphs may be named views over this graph, but MUST NOT persist independent edge truth or implement divergent dependency semantics.

Each edge has stable identity, endpoint identities, type, provenance, validity/knowledge state, and any boundary-specific condition. Derived edges identify their input facts and rule version. Conflicts remain represented; precedence requires an explicit `Decision`. Cycles are accepted or rejected by edge-type policy, never by a global assumption that all relations are DAGs.

Resource conflicts constrain scheduling rather than invalidating otherwise valid work. A valid `WorkUnit` may be not-ready or temporarily unschedulable because another unit holds or requires an overlapping resource. Conflict resolution changes readiness/schedule projections, not the work's validity, requirements, or authorization.

## 7. Authorization and runtime trust

Planning never grants authorization. A `Requirement`, `WorkUnit`, plan, frontier, inferred effect, risk classification, or `EffectRequest` can establish what should happen or what permission is needed; only a valid `CapabilityGrant` from an accepted authority can establish permission. A grant is bound to exact subject, capability/effect, scope, issuer, conditions, and freshness. It does not prove the effect is supported, safe, attempted, or successful.

KEEL autonomy may not exceed observed runtime trust. The effective autonomy ceiling is the intersection of repository policy, valid grants, observed `RuntimeProfile`, Codex/tool/sandbox constraints, and external-system controls. Missing, stale, ambiguous, conflicting, configuration-only, or unverified runtime evidence lowers the ceiling; it is never upgraded optimistically.

Hooks are runtime adapters and guardrails, not assumed confinement. They translate kernel context/policy into Codex hook events and collect observations where supported. Specialized tools, alternate clients, direct processes, configuration drift, or untrusted project hooks may bypass them. Independent reconciliation and verification remain mandatory; sandbox, approvals, host controls, provider authorization, and protected Git infrastructure remain load-bearing.

Codex-native subagents and workspaces are runtime resources. KEEL may express work ownership, isolation requirements, resource conflicts, and evidence expectations, but MUST NOT implement a second agent scheduler or workspace authority.

## 8. Exact subjects, evidence, and verification boundaries

Evidence is meaningless without an exact subject identity. Every `EvidenceRequirement`, `EvidenceReceipt`, `Decision` that relies on evidence, and `Attestation` MUST name the subject it supports: canonical record IDs plus content/tree/commit/intent/config/runtime digests as applicable. Path-only, branch-name-only, mutable-file-only, or conversational claims are insufficient for completion.

A receipt records at minimum provider identity and version/provenance, exact inputs, exact subject, observed runtime/environment identity to the degree required by policy, start/end or freshness basis, literal result, bounded artifact references, and integrity digest. Reusing a receipt for another subject requires a deterministic equivalence rule and a recorded `Decision`; similarity is not equivalence.

Candidate verification and integration verification are distinct:

- **Candidate verification** evaluates an exact proposed content tree and canonical intent before integration. It can create a candidate `Attestation`; it cannot claim landed state.
- **Integration verification** independently evaluates the exact landed subject and integration context after merge/rebase/squash or equivalent. It must prove content/intent equivalence where receipts are reused and run integration-specific evidence where context can alter behavior. Only it can create a landed `Attestation`.

A seal is a candidate-bound operation. An anchor is a landed-state operation. The future landing transaction may coordinate operations, but this planning turn neither defines its implementation nor permits integration to skip either boundary.

The current migration now factors exact Git proof into `.keel/lib/git_proof.py` and a
versioned `CandidateAttestation` into `.keel/lib/candidate_attestation.py`. The
attestation is a canonical Git blob indexed separately from the preserved candidate
commit ref; refs and notes remain mutable anchors. This extraction preserves the
existing seal/anchor integration boundary and explicitly does not implement the
Landing Transaction planned for a later turn.

## 9. Canonical intent and reconciliation

Human intent enters as source-attributed `Requirement`, `Decision`, policy, and requested outcomes. `WorkUnit` decomposition is a deterministic/provenance-bearing interpretation of that intent, not authority to broaden it. Scope, effects, evidence obligations, and allowed uncertainty narrow through decomposition unless an accepted authority explicitly decides otherwise.

Reconciliation compares canonical expected state, observed repository/runtime/external facts, receipts, attestations, and Git state. It reports differences and proposes legal next actions; mutation requires a separately authorized effect. The future reconciler MUST be idempotent for equal inputs and MUST preserve conflicts rather than picking an authority implicitly.

No later subsystem may create a second semantic authority. Specifically, CLI state, hook caches, context packets, dashboards, mission files, generated maps, test fixtures, provider payloads, telemetry, benchmark data, plans, and agent messages are inputs, receipts, or projections. If they disagree with canonical kernel records, reconciliation exposes the disagreement; consumers do not choose independently.

## 10. Compatibility and migration invariants

1. Old formats remain readable until deterministic migration and compatibility exist. This includes landed ledger schemas, mission v1/v2, repository-intelligence output, evidence graphs, effects/authorization files, config/contracts, bootstrap manifests, refs and notes.
2. Readers migrate before writers. A new reader must deterministically parse/classify every supported old fixture before any default writer changes.
3. Every migration is versioned, deterministic, idempotent, provenance-preserving, and reversible or accompanied by a verified recovery path. It emits old/new subject digests and never invents authority, grants, evidence, or runtime observations.
4. Dual-read may precede canonical-write; dual-write is forbidden unless byte/semantic equivalence and failure atomicity are mechanically proven. One format is named canonical at every stage.
5. Unknown or unsupported legacy fields survive losslessly or block migration. Silent dropping, optimistic defaulting, and semantic status collapse are forbidden.
6. Historical ledgers, refs, notes, and attestations are append-preserved evidence. Migration may add linked representations; deletion waits for repository-wide compatibility, recovery, and retention decisions.
7. Generated artifacts change only through their declared producer. The bootstrap manifest must be regenerated, never hand-edited, when its tracked source set requires it.
8. Each migration stage is a separate KEEL change with exact scope, risks/effects, behavioral acceptance, independent compatibility fixtures, candidate verification, seal, authorized integration, integration verification, and landed anchor.
9. A legacy surface can be removed only after all in-repository readers/writers and documented external compatibility obligations have deterministic replacements, downgrade/recovery is resolved, and an explicit `Decision` records the removal gate.
10. Until the new canonical graph and primitives are landed, existing lifecycle enforcement remains governing current writes; this document governs only the target and migration constraints.

1. `authority_id: KEEL-KERNEL-REDESIGN-v1` and one stage from M1-M6;

If a later design cannot be expressed with the canonical primitives and one graph, it must stop and amend this authority rather than create an exception locally. If repository evidence contradicts a baseline observation here, record a `Fact`/`Decision`-backed amendment; do not silently fork semantics.
